# Cloud Resume Challenge — Technical Documentation

This document records how I built, deployed, automated, and containerized my portfolio as part of the Cloud Resume Challenge.

The project started as a simple React portfolio and gradually became a small cloud-native application using AWS, GitHub Actions, and Docker.

---

# 1. Frontend

The portfolio is built with:

* React
* TypeScript
* Vite

The production application is generated with:

```bash
npm run build
```

This creates the production files inside:

```text
dist/
├── index.html
├── assets/
└── ...
```

Those static files are then used by the hosting infrastructure.

# 2. Running the Project Locally

## Installing Node.js

While working on the portfolio, I needed to run the usual frontend commands such as:

```bash
npm run
```

and:

```bash
npm run build
```

At one point, the project required a newer Node.js version than the one available on my Mac.

I initially thought:

> Hell no . This laptop is literally the most modern thing I have.

Instead of replacing anything on the system manually, I installed Node.js using **FNM (Fast Node Manager)**.

FNM is a Node.js version manager that allows different Node.js versions to be installed and selected easily.

After installing FNM, I could install and use the required Node.js version and continue working normally with npm.

The important lesson was not really Node.js itself. I simply needed the correct runtime version so the project could build successfully.

# 5. HTTPS Certificate and the AWS Region Problem

One of the first AWS problems that confused me was the SSL/TLS certificate.

I created my certificate with **AWS Certificate Manager (ACM)** in my normal AWS region.

Later, when I went to configure the certificate for my CloudFront distribution, I could not find it.

At first, this looked like a bug.

It was not.

The reason is that **CloudFront requires its ACM certificate to be created in the `us-east-1` region (N. Virginia)**.

So even though the rest of my infrastructure could be in another AWS region, the certificate used by CloudFront had to exist specifically in:

```text
US East (N. Virginia)
us-east-1
```

The final setup became:

```text
ACM certificate
      │
      │ us-east-1
      ▼
CloudFront
      │
      ▼
S3
```

This was a good reminder that AWS services do not always follow the same regional rules.

# 7. Serverless Visitor Counter

The portfolio includes a visitor counter built with serverless AWS services.

The architecture is:

```text
Browser
   ↓
API Gateway
   ↓
Lambda
   ↓
DynamoDB
```

### API Gateway

API Gateway exposes the HTTP endpoint used by the frontend.

### Lambda

Lambda contains the backend logic.

It receives the API request, interacts with DynamoDB, and returns the result to the frontend.

### DynamoDB

DynamoDB stores the visitor count.

This allowed me to implement the backend functionality without running a traditional server.

# 8. CORS — The Pain 

CORS was one of those things that somehow appears everywhere.

The problem happened because the frontend and API were not considered the same origin.

The browser therefore required the API to explicitly allow requests from the frontend.

For API Gateway, I needed to configure CORS for the API resource and allow the required HTTP method, in my case the `GET` request.

I also needed the Lambda response to include the appropriate CORS headers, for example:

```text
Access-Control-Allow-Origin: *
```

The basic flow became:

```text
Browser
   ↓
GET /visit-count
   ↓
API Gateway
   ↓
Lambda
   ↓
Response
   ↓
Access-Control-Allow-Origin
```

My initial reaction to CORS was basically:

> CORS... seriously? These things are everywhere. 

But working through it made the important concept clear:

**CORS is enforced by the browser, and the API must explicitly communicate which origins are allowed to access it.**

For this personal project, I used:

```text
Access-Control-Allow-Origin: *
```

because the API did not contain sensitive user-specific data.

# 9. Visitor Count Increased on Every Refresh

Another issue appeared after the visitor counter was working.

Every time I refreshed the portfolio, the visitor count increased.

At first I thought:

> Wait... why is the counter doing that? 

The reason was simple.

The frontend sends the API request whenever the page loads.

Therefore:

```text
Page load
   ↓
GET /visit-count
   ↓
Lambda
   ↓
DynamoDB
   ↓
count + 1
```

Refreshing the page triggers the same process again.

This means the current implementation is counting **requests/page loads**, not guaranteed unique human visitors.

A real unique-visitor system would require additional logic, such as identifying visitors through a cookie, session, IP-based strategy, or another tracking mechanism.

For this project, I kept the simpler implementation because the goal was to demonstrate the complete serverless architecture.

# 11. The `.github/workflows` Mistake 

This one took me longer than it should have.

My repository contains the portfolio inside a subdirectory:

```text
cloud-resume-challenge/
└── z13i-portfolio/
```

While working inside the portfolio directory, I created:

```text
z13i-portfolio/.github/workflows/
```

and placed my workflow YAML file there.

Then I pushed the changes and waited for GitHub Actions to appear in the **Actions** tab.

Nothing.

I checked the workflow several times and wondered what I had done wrong.

The problem was the location.

GitHub Actions looks for workflow files in:

```text
.github/workflows/
```

at the **repository root**.

The correct structure was:

```text
cloud-resume-challenge/
│
├── .github/
│   └── workflows/
│       └── deploy.yml
│
├── z13i-portfolio/
│   ├── src/
│   ├── public/
│   ├── package.json
│   └── ...
│
└── README.md
```

Not:

```text
cloud-resume-challenge/
└── z13i-portfolio/
    └── .github/
        └── workflows/
```

The lesson was simple:

> When working with GitHub Actions, remember that `.github/workflows` belongs to the repository root, not necessarily to the folder containing the application.

After moving the workflow to the correct location, GitHub detected it.

# 12. Dockerizing the Portfolio

After the AWS deployment was working, I also containerized the portfolio.

The Dockerfile uses a multi-stage build.

```text
Stage 1
Node.js
   ↓
npm ci
   ↓
npm run build
   ↓
dist/

Stage 2
Nginx
   ↓
copy dist/
   ↓
serve static files
```

The first stage uses Node.js because Node and npm are needed to build the React application.

The second stage uses Nginx because the resulting application is just a collection of static files.

The generated `index.html`, JavaScript, CSS, and assets are copied into Nginx's web root:

```text
/usr/share/nginx/html
```

Nginx then serves those files to the browser.

This results in a smaller final image than keeping the complete Node.js build environment in the production container.

They did not.

Node needed a newer version → installed FNM.

CORS → of course CORS.

Very educational. Very peaceful. Totally no suffering.
